## Executive assessment

RSI-Chip is a broad Rust research and prototype EDA toolkit. It already contains RTL elaboration, digital simulation, a simplified synthesis flow, SAT/BMC/equivalence/induction checking, STA/MMMC/SDC support, prototype placement and routing, AMS simulation, statistical analysis, power/IR/EM analysis, physical verification helpers, verification-quality utilities, browser editors, CLI/API/daemon surfaces, and regression infrastructure.

It is not yet a Cadence- or Synopsys-class production flow, a certified foundry signoff environment, or a tapeout-quality implementation system. In particular, certified PDKs, TCAD, advanced compact models, FastSPICE, signoff extraction, foundry DRC/LVS, GDSII/OASIS stream I/O, thermal and package analysis, emulation, protocol VIP, memory repair, and production ATE/yield flows are absent or only partially represented.

The roadmap below separates three different kinds of work:

1. Capabilities that Cadence and Synopsys-class vendors provide and RSI-Chip does not meaningfully provide.
2. Capabilities for which RSI-Chip has a useful prototype or subset but not commercial strength.
3. Product, architecture, circuit, firmware, and workload decisions that must be supplied as design inputs; an EDA system can model or verify them, but it should not invent them.

## Reading guide

| Field | Meaning |
|---|---|
| `Progress` | An engineering-readiness estimate for RSI-Chip, not a schedule estimate or foundry qualification result. |
| `Missing` | No meaningful implementation exists in the repository. |
| `Incomplete` | An implementation, parser, model, engine, API, editor, or tests exist, but commercial semantics, scale, accuracy, interoperability, or certification are insufficient. |
| `Design input, not EDA scope` | The item is owned by the architecture, design, firmware, product, or manufacturing team. EDA tools consume its specifications, models, traces, constraints, or golden results. |
| `P0` | A tapeout or signoff blocker for a competitive GPU or advanced-memory device. |
| `P1` | A major commercial-capability gap, but a project can sometimes proceed with an external point tool. |
| `P2` | Important productivity, scale, interoperability, or ecosystem work. |
| `P3` | Useful industrial hardening after core capability is established. |

Progress ranges used here:

| Range | Meaning |
|---|---|
| `0%` | Not started. |
| `1-15%` | Research concept, isolated parser/model, or narrow demonstration. |
| `16-35%` | Foundational subset with real APIs and tests, but major semantic and scale gaps. |
| `36-60%` | Engineering prototype useful for internal experiments, but not signoff grade. |
| `61-80%` | Pre-production capability requiring industrial hardening and external qualification. |
| `81-95%` | Production candidate with remaining integration or certification work. |
| `96-100%` | Certified, production, or tapeout-signoff ready; no item below is in this range. |

## 14. Hard blockers for a credible GPU or advanced-memory tapeout

| No. | Blocking area | Why it blocks signoff | Commercial reference | Minimum exit criterion |
|---:|---|---|---|---|
| H1 | Process and certified PDK source | Design rules, devices, models, extraction, reliability, and manufacturing outputs cannot be certified by the EDA project alone. | Foundry PDK ecosystems | A foundry-authorized PDK version is imported and correlated against golden test structures. |
| H2 | Full compact models and calibration | Circuit timing, power, noise, retention, aging, and reliability predictions remain uncalibrated. | HSPICE, Spectre, FineSim, CustomSim | Selected model correlation meets published process-specific tolerance and provenance requirements. |
| H3 | GDSII/OASIS and complete physical databases | Without exact stream and physical-object semantics, a layout cannot be reliably exchanged or manufactured. | Pegasus, PVS, IC Validator, Virtuoso | Round-trip and foundry-reader validation on all required layout objects. |
| H4 | Signoff DRC/LVS and parasitic extraction | Geometry legality, schematic/layout equivalence, and signoff RC are mandatory before tapeout. | IC Validator, Pegasus, PVS, StarRC, Quantus | Complete deck execution and independent golden-case agreement with signed reports. |
| H5 | FastSPICE and memory-array simulation | DRAM/NAND sense, retention, disturb, programming, and full-array checks cannot be replaced by small SPICE circuits alone. | Spectre FX, FineSim, CustomSim/XA | Partitioned array simulation with bounded error and runtime on representative memory blocks. |
| H6 | Industrial digital implementation and timing closure | A top GPU cannot close timing, congestion, power, DRC, MMMC, and ECO objectives with only prototype optimization. | Fusion Compiler, IC Compiler II, Genus, Innovus, PrimeTime, Tempus | Hierarchical benchmark closure with reproducible QoR and regression evidence. |
| H7 | Variation, SI, and accurate parasitic timing | Advanced-node signoff requires variation models, coupling, noise, and accurate delay calculation. | PrimeTime SI, Tempus SI, StarRC, Quantus | SI/variation methods correlate against golden extracted-network cases. |
| H8 | Thermal, electrothermal, and package analysis | AI-training power, HBM stacks, and multi-die packages cannot be released without credible thermal/PDN margin. | Cadence Celsius, Sigrity, Clarity, Voltus-Fi; Synopsys thermal/3D-IC flows | Coupled electrothermal/package scenarios meet traceable accuracy and convergence requirements. |
| H9 | Protocol, PHY, and memory-interface verification | DDR/LPDDR/HBM, ONFI/Toggle, SerDes, training, ECC, and controller behavior need protocol-aware signoff. | Synopsys VIP, Cadence VIP, SerDes tools | Protocol checker and PHY/channel reference reproduce all mandatory compliance cases. |
| H10 | Test, repair, and yield flow | Memory products require redundancy, fuse/OTP programming, KGD, diagnostics, and manufacturing traceability. | TetraMAX, Modus, memory repair ecosystems | Repair allocation, programming data, wafer/stack test records, and release manifests are traceable end to end. |

## 16. Roadmap conclusion

The most credible next phase is not to add more isolated features first. A defensible path is:

1. Select one external process/PDK source and one concrete signoff vehicle.
2. Implement exact physical database exchange for that process, especially OASIS/GDSII, LEF/DEF, Liberty, SPEF, and SDC.
3. Make one digital block and one analog block pass independently correlated DRC/LVS/RC/timing/power checks.
4. Add a FastSPICE-class memory-array path and one protocol/PHY verification target.
5. Add thermal/package co-analysis before claiming an AI-GPU or HBM signoff flow.
6. Keep architecture and firmware decisions as explicit design inputs with versioned golden models.
7. Treat every new feature as incomplete until it has external-format compatibility, scale, uncertainty, reproducibility, and independent correlation evidence.
